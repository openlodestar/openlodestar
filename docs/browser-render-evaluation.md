# 浏览器渲染：代价评估与定向实测（0/2 可核，这条路已关闭）

> 触发：抓页可核那一轮里，**被拦 6 条 + 脚本壳 2 条**拿不到正文，只能靠真浏览器。
> **最终结论（2026-11-09 实测后）**：用本机已缓存的 Chromium 对最可能核上的两页做了定向实测，**0 页可核**。按事先约定，把"渲染对中文证据基本无效"写成结论并**关掉这条路**：不默认开、不列必装、评分卡不新增分项，也不再反复评估。
> 本文保留完整算账过程与实测证据；冻结样本在 `examples/replay-search/porcelain-2021-autumn/render-checks.json`。

## 先纠正一个前提：渲染能力已经存在，缺的不是依赖

仓库里已经有 `plugins/browser-playwright/`（独立工作区包，playwright 依赖只写在它自己那份 `package.json` 里），核心包的 `dependencies` 仍然只有 `js-yaml`。单页抓取 `src/integrations/scraper-strategies/single-page-fetch.ts` 的策略是「裸 fetch → 失败后浏览器降级」，而且 `allowBrowser` **默认就是开**。

所以真正待决定的不是"要不要引入浏览器"，而是两件更小的事：

1. **评分卡的抓页采样要不要默认开渲染**（现在 `capture-page-checks.ts` 写死 `allowBrowser: false`）；
2. **要不要把 Chromium 内核列为使用者首次运行的必装项**（现在要手动 `pnpm run browser:install`）。

## 四条可选路径与代价

| 路径 | 要改什么 | 安装体积 | 首次运行 | CI | 离线 |
| --- | --- | --- | --- | --- | --- |
| A. 内置 Playwright（现状能力，改成默认开） | 抓页脚本加 `--allow-browser`；文档写清 `browser:install` | npm 包 **4.7 MB**（已在工作区里）；Chromium 内核本机实测 **684 MB**（chromium 413 MB + headless shell 267 MB + ffmpeg 3 MB） | 不跑 `pnpm run browser:install` 就抛 `BrowserUnavailableError`，断言按 `paused` 处理 | 现在 `pnpm test` 用假模块，**不需要浏览器**；若 CI 要真渲染，得加一步 `browser:install`（可缓存） | 装完之后浏览器启动不依赖外网；但渲染本身仍要联网取页 |
| B. 调系统已装 Chrome / Edge | 插件加一个 `channel` 或 `executablePath` 选项（约十行） | **0**（用系统浏览器） | 机器上得有 Chrome / Edge；Windows 自带 Edge，GitHub 托管 runner 自带 Chrome | 可以，但渲染结果随浏览器版本漂 | 同 A |
| C. 使用者自备外部渲染服务 | 写一个第三方 `BrowserRenderer` 插件并注册，核心不改 | 0 | 要配 endpoint 与凭据 | 要凭据，PR 场景不可用 | **不可**：离线直接没材料，冻结回放也失效 |
| D. 不支持，只标"需要渲染" | 不需要改（现状） | 0 | 无 | 无影响 | 完整 |

三条补充事实：

- **A 的体积主要不是 npm 包，是内核。** `pnpm install` 只装 4.7 MB 的 playwright 包；684 MB 是执行 `playwright install chromium` 之后的磁盘占用。仓库当前**没有**把这一步放进任何默认脚本。
- **B 的代价在可复现性。** 系统 Chrome 自动升级，同一份冻结样本换台机器可能渲染出不同 DOM；要用 B 就得把浏览器版本写进样本说明。
- **C 与"冻结回放、零外部调用"直接冲突。** 评分卡的前提是样本冻结后重跑不再联网，外部渲染服务把这个前提打掉。

逐查询推：

- **porcelain 第 1 条源查询**：中文候选只有 thevalue 这一页 → 渲染成功且三个字段逐字命中，才可核。
- **porcelain 第 4 条源查询**：中文候选只有 artron → 同上。
- **cg 两条候选查询**：候选全是英文站或付费墙 → 即使渲染成功，中文机构名/专场名/日期也几乎不可能逐字出现。

**结论区间**：

| 口径 | 渲染后 | 说明 |
| --- | --- | --- |
| 只看用户点名的 8 条 | **0/8 ～ 1/8 = 0～12.5%** | 唯一希望是 artron 一页；日期格式一漂就回到 0 |
| 把 thevalue 也算上（9 页） | **0/8 ～ 2/8 = 0～25%** | 两条 porcelain 查询各赌一页中文正文 |
| 抓页成功率（顺带会好看） | 1/13 → 最多 9/13 ≈ 69% | **这项会明显变好，但它不是目标读数** |

**别拿抓页成功率当收益。** 渲染能让 6 条被拦 + 2 条壳"抓到"，但其中 7 条是英文站，正文里没有我们要的中文字段，可核率最多加 1～2 条。如果只看"抓页成功率从 7.7% 涨到 69%"就拍板引入 684 MB 内核，等于花大钱买了一个不解决核心问题的指标。

**会误判的地方**：以上是按站点语言与字段语言推的，没有真渲染。artnet 可能对无头浏览器继续 403；artron 可能有反爬；thevalue 的正文也可能不含完整专场名。所以给的是区间，不是承诺。

## 定向实测：两页，0 页可核

按上面的推断，最可能核上的只有两条中文页。用本机 **已缓存** 的 Playwright Chromium（未下载内核、未改 `package.json`、未动 CI）逐页渲染，等 `domcontentloaded` + `networkidle`、**滚到底再多等 3 秒**（排除懒加载误判），再用与抓页样本完全相同的 `processHtml` 清洗、`judgePageFields` 逐字判定。

| 页面 | 渲染结果 | 机构（北京保利） | 专场（禹贡Ⅰ—盛清御瓷新风尚） | 日期（2021年12月5日） | 判定 |
| --- | --- | --- | --- | --- | --- |
| artron.net/auction/2021-winter-poly-auction-catalog | 正文 **0 字符**；页面标题是「雅昌艺术网:传艺术之美-权威艺术门户网站」 | ✗ | ✗ | ✗ | **不可核**：这个地址渲染后落到站点首页，本身就是无效图录页 |
| thevalue.com/auctionnews/117655 | 正文 **1429 字符**（此前两次分别 2369 / 1691 字符）；标题是站点门户标题 | ✗ | ✗ | ✗ | **不可核**：渲染出来只有导航与页脚壳，文章正文不在 DOM 里 |

补充证据：

- 两页逐字检索 `北京保利`、`保利`、`禹贡`、`2021年12月5日`、`12月5日`、`盛清御瓷`，**全部为 false**——不是日期格式写法差异导致判不中，而是正文里根本没有这场的信息。
- artron 一页跑了 4 次，每次都只有站点首页壳（64 KB HTML、清洗后 0 字符）。
- thevalue 一页共 4 次尝试：3 次渲染成功（2369 / 1691 / 1429 字符，均无关键字段）、1 次 `page.goto` 30 秒超时。**抖动会让人误以为"再试一次就好了"，但三次成功渲染都没拿到正文。**
- 冻结样本只存字符数、标题、逐字段判定与尝试摘要，**不存正文**；它不参与评分卡，也不进任何样本锁。

**这组实测推翻了预估里"artron 大概率能核上"的那格。** 原因不是渲染失败，而是**这两个地址本身不是有效的正文页**：一个重定向到首页，一个是纯前端壳（正文由接口或交互加载，滚动与等待都拿不到）。中文站里能渲染出正文的页面也许存在，但本轮样本里没有——而"换一批样本再找找"正是被要求关掉的那条反复评估的路。

| 问题 | A 内置 Playwright | B 系统浏览器 | C 外部服务 | D 不支持 |

| 安装体积 | +4.7 MB（已含）；内核另 684 MB | 0 | 0 | 0 |

## 结论：关掉这条路

**结论：不把渲染接进评分卡，也不做"按站点触发"的可选能力。** 实测两页 0 可核，而这两页是整批候选里唯二的中文页；继续投入就是拿 684 MB 换一个大概率仍为 0 的读数。

落地的四件事：

1. **评分卡不新增分项**，抓页样本的 `allowBrowser` 保持 `false`，三个读数维持"被拦 / 结构不符"的原样记录——那些档位已经准确表达了"拿不到可核材料"。
2. **`package.json` 不动**，Chromium 不列为必装。渲染能力作为插件留在仓库里，谁需要谁自己装（现状）。
3. **不再围绕渲染反复评估**；本次实测证据冻结在 `render-checks.json`，后续有人再提，先读这份样本。
4. **"渲染对中文证据基本无效"写成本轮结论**，限定条件是：本批两份样本、24 个候选页里的两个中文页、一次定时实测。它不是"渲染永远没用"的定律。

**这条结论在以下情况失效（届时才重新开评估，且要先有新证据）：**

- 出现**新的候选页**（换批次或换站点）且抓页分档显示它是中文站、脚本壳、且摘要里明确点名本场——这时先只对那一页做同样的单页实测，不重开整条评估；
- 站点改版让 artron / thevalue 的正文进入 DOM（可用同一份 `render-checks.json` 的字段与判据复测）；
- 目标产品改成以英文站为主（字段值也变英文）——那时"英文正文对不上中文字段"这条主要理由才消失；
- **不包括**"想提高抓页成功率"：那项从 7.7% 涨到 69% 也不解决可核率，不能作为重开理由。

## 本轮边界（如实）

- **没有改 `package.json`，没有下载浏览器内核。** 用的是本机此前已有的 `ms-playwright` 缓存；本轮只启动了它，没有安装。
- **真渲染了 2 页、共 8 次尝试**（artron 4 次均为首页壳；thevalue 4 次里 3 次渲染成功、1 次超时），结果如实写进冻结样本；没有为了"再试一次"而扩大样本。
- 这次实测不覆盖：登录墙、验证码、视频/PDF 内容、渲染耗时对 15 秒抓页超时的影响；也不代表其它中文站。
- `render-checks.json` 是**证据文件**，不被评分卡读取、不进样本锁，删掉它不影响任何读数。
