# 好演示的写法：从一句可核对的话，到一张能复查的收据

这份指引写给要做产品演示的人。它不讨论某个具体演示哪里不好，只回答一个问题：

> 怎样设计一个让人愿意相信、而且能自己动手核对的演示？

下面每一条都尽量写成"怎么做"，而不是"不要怎么做"。最后附一个已经落地的完整案例，可以直接对照。

## 一、先算一笔账：演示的价值从哪里来

一个演示值不值得做，可以用一条粗糙但好用的式子排序：

```
演示价值 ≈ 错误代价 × 模型出错概率 × 观众可核验度 − 演示成本
```

四个因子分别是什么意思：

| 因子 | 问的问题 | 对演示的影响 |
| --- | --- | --- |
| 错误代价 | 这句话如果是错的，谁会付出什么代价？ | 代价越高，核验越有价值；答错无所谓的题目，演示会显得没事找事 |
| 模型出错概率 | 模型有多可能"听起来很有把握，其实是错的"？ | 概率越高，核验层越有戏份；太简单的题，谁做都对 |
| 观众可核验度 | 观众能不能不依赖你，自己打开原始来源核对？ | 越高，演示越像证明；越低，越像表演 |
| 演示成本 | 观众理解、运行、核对各要多久？ | 超过几分钟，价值会被成本吃掉 |

这条式子不是精确计算，是排序工具：先挑"错了代价高、模型容易错、观众能自己查"的题目。任何一项接近零，整个演示就接近零。

## 二、演示是证明，不是功能导览

功能导览回答"我们有什么"；演示回答"你凭什么信"。

一个好的演示结束时，观众应该能复述三件事：

1. 你核了什么；
2. 你用什么核的；
3. 你拒绝了什么。

如果观众看完只记得"界面挺好看"或者"讲得挺流畅"，演示没有完成它的任务。把演示当成一份**可复核的证词**：结论、证据、出处、反证、边界，五样齐全。少一样，观众就多一分"这是不是剪出来的"的怀疑。

## 三、从一句话开始，而不是从一个页面开始

演示的单位不是屏幕，是一句话。这句话要具体到能被推翻：

- 有时间、有主体、有事情、有可查的出处。
- 反例："我们的系统能分析拍卖市场。"
- 正例："2021 年 12 月 5 日，北京保利举办了「禹贡Ⅰ—盛清御瓷新风尚」专场。"

这句话最好来自模型的真实输出，而不是你替它编的"标准答案"。你要演示的是"模型说的这句话能不能信"，不是"我能不能背出正确答案"。

一句话还要能拆成字段：机构、时间、专场名、地点。**字段是核验的最小单位，段落是叙事的单位**。先拆字段，再拼故事；反过来做，就会把"这句话大概是对的"当成"每个细节都成立"。

## 四、三幕叙事：诱饵、拆解、裁决与拒绝

一个完整的产品演示通常有三幕。

**第一幕：诱饵。** 给出一句听起来合理的话。它最好"大部分是真的"——真实的主体、真实的季节、真实的品类，只有一个关键细节错了。这样的诱饵才像真实世界里的错误；一眼假的稻草人，打赢了也不说明问题。

**第二幕：拆解。** 把这句话拆成字段，逐字段找证据。观众看到的是：哪个字段有两条独立来源，哪个字段只有一条，哪个字段根本没人提。这里要让观众看到"来源家族"的概念（同一篇原创稿被不同网站转载，仍然只算一个来源），否则"两个网站"很容易被误读成"两个独立证据"。

**第三幕：裁决与拒绝。** 把字段拼回记录：关键字段是否全部成立？是否有同一个页面同时写到全部关键字段？最后的门禁（gate：决定这条记录能不能导出坐标的最后一关）给出三种结局——强、弱、拒收。然后明确说出：这条记录给不给坐标（anchor：可供下游再入的记录身份，不是网页链接），为什么。

三幕的终点不是"答案"，是"可用的结论 + 不可用的理由"。观众记住的往往是后者。

## 五、真实素材，冻结使用

用真实公开页面。真实素材自带一个合成数据永远给不了的属性：**观众可以自己去查**。

但演示时不要依赖实时抓取。把页面抓下来、存成快照（snapshot：核验时读到的那一版页面正文）、记录原始 URL 与抓取日期，然后用快照重放。理由有三条：

1. **可复现**：同一份底稿，今天和明天跑出同一个结论。
2. **可核对**：观众可以拿快照和原页对照，确认你没有改字。
3. **可控制**：现场网络、反爬、登录墙不会把演示变成事故。

"冻结"不等于"编造"。冻结的是"核验时读到的那一版正文"，原页链接仍然在；合成数据没有原页，冻结数据有。两者在演示里的可信度不是一回事。

把抓取方法写出来：什么时候抓的、用什么抓的、正文怎么清洗的、哪些内容被丢掉了。接缝露出来，信任才立得住。

如果一定要现场抓一页，把它放在最后作为"加演"，不要让主结论依赖它。

## 六、让拒绝成为主角

只展示成功的演示，证明不了产品；任何人都能剪一个成功集。

一个可信的演示至少要有四种结局中的三种：成立、被反驳、未查到、互相冲突。最好每种都有。其中"未查到"还要再说清是哪一种：预算没跑完、候选里没有能承载它的来源、还是覆盖完了确实没有。这三种"不知道"的含义完全不同，混在一起说，等于把"没查"包装成"没有"。

拒绝必须由同一套代码算出，不能手写"这条我们拒了"。观众一旦发现拒绝是安排的，就会怀疑成功也是安排的。

把"我们不下结论"当成产品能力写进演示。核验产品的价值，一半在敢说"是"，一半在敢说"不知道"。

## 七、把证据放在结论旁边

观众从结论走到原句，最好不超过三次点击或三次目光移动。

每个结论旁边放五样东西：

- 一条逐字引文；
- 一个来源域名；
- 一个来源家族（同源转载、镜像、跨语言站归并后的身份）；
- 一个档位（官方、一手、聚合、未列名）；
- 一个快照引用（能落到具体文件）。

不要用"据权威来源"这种话。权威不是形容词，是可数的独立家族。

视觉上，结论在前，证据在后，方法最后。不要让观众先读架构图才知道发生了什么。报告的排版应该像案卷或收据：字号克制、层次清楚、颜色只用来编码结论（成立、拒绝、弱），不用来装饰。收据不是账单本身，但它让你能核对账单。

## 八、一个可复现的交付物

一份演示应该有一个"入口"：一条命令、一个 HTML、一个不需要登录的页面。入口要满足：

- 断网能跑，或者至少断网能看；
- 不需要 API key；
- 三分钟内能看到第一个结论；
- 所有数字由同一条命令生成，没有手改的"展示版"。

如果演示需要二十分钟讲解才能看懂，它是汇报，不是演示。

单文件 HTML 是很好的载体：好转发、好存档、好打印，不会因为服务下线而消失。把 CSS 内联进去，不要引用外部字体、脚本或图片；演示的寿命不应该取决于某个 CDN。

## 九、把演示纳入测试

演示是"带叙事的回归测试"。它一旦和实现漂移，就会变成第二种真相：文档说着、代码不是这么跑。

把示例底稿放进测试：

- 引文必须逐字命中自己的快照；
- 裁决与门禁必须与引擎当前实现一致；
- 报告必须能生成，且不能出现 `undefined` 或 `[object Object]` 这类占位物。

在 CI 里跑。改坏示例，测试先红。这样演示不会腐烂。

演示里的每个数字都要能由命令重算。发现一个手写数字，就删掉或改成生成。**演示不是营销素材，它是产品的一个可执行断言。**

## 十、契约测试与产品演示，分工不同

合成数据不是坏东西，它适合另一件事。两者的分工可以写成一张表：

| 用途 | 素材 | 目的 | 是否进 CI |
| --- | --- | --- | --- |
| 契约测试 | 合成、可控 | 覆盖每一种形状：四种裁决、三种门禁、缺失字段、冲突来源 | 是 |
| 产品演示 | 真实、冻结 | 回答"这套东西在真实世界的写法上管不管用" | 是（作为回归） |

合成数据可以精确制造边界情况，但它不能回答"观众能不能自己去查"。产品演示要用真实素材；契约测试要用合成素材。两者不要互相替代。

## 十一、观众分层，不分层真相

技术观众想看数据契约、门禁逻辑、硬护栏的读数；业务观众想看错误代价、拒绝理由、能不能少赔钱；普通观众只想看一句真话、一句假话、一张收据。

同一份证据，做三个入口，不要做三个版本的事实。第一屏同时回答：问了什么、查到了什么、拒绝了什么。细节放在后面，让想深入的人自己往下走。

## 十二、边界要写出来

一个诚实的演示，最后一节应该叫"这个演示没有证明什么"。

写清这些：

- 数据是冻结的，演示只重算已有证据，不重新检索、不重新抓取、不调用模型；
- 来源覆盖有限，哪一类来源没有纳入，因此哪条结论只能到弱档；
- 负样本是注入的，`not_found` 说的是"这批证据里没有"，不是"世界上不存在"；
- 快照是正文文本，不是浏览器完整 DOM；原始 URL 与抓取日期在哪里。

边界不会削弱演示，反而会让前面的结论更可信。观众会想：连边界都说了，别的地方大概没吹。不要用"仅供参考"当万能免责声明；要具体到"哪一批来源没覆盖、哪一个结论因此只能到弱档"。

## 十三、清单

**开工前**

- [ ] 一句话能说清要核什么，具体到时间、主体、事情。
- [ ] 这句话有一个"看起来合理"的错误版本。
- [ ] 真实版本至少有两个独立来源；错误版本至少有一个可以反驳它的来源。
- [ ] 观众能自己打开原页核对。
- [ ] 演示能离线重放。

**制作中**

- [ ] 每个字段都有裁决，每个裁决都有引文。
- [ ] 至少包含一个强记录、一个弱记录、一个拒收记录。
- [ ] 拒绝是算出来的，不是写死的。
- [ ] 报告里每个数字都能由命令重算。
- [ ] 来源家族按原创方归并，转载不算独立票。

**交付前**

- [ ] 陌生人三分钟能复述结论。
- [ ] 所有引文通过逐字护栏。
- [ ] 演示在 CI 里有测试。
- [ ] 边界写在报告里。
- [ ] 没有孤立数字、没有手改的"展示版"。
- [ ] 断网、无 key、单文件可打开。

## 十四、叙事模板

可以直接套用这个骨架：

```
标题：<主体> 在 <时间> 的 <一件事>
一句话：<可核对的具体断言>
诱饵：模型给出的版本是 <看起来合理的说法>。
陷阱：其中 <字段> <错了 / 没有证据 / 只有单一来源>。
裁决：<成立 / 被反驳 / 未查到>，依据是 <引文>（<来源>，<家族>）。
拒绝：因此 <不导出坐标 / 只给弱坐标>。
边界：这批证据没有覆盖 <X>；要证明 <Y> 还需要 <Z>。
```

把它填满，演示的骨架就有了。剩下的工作是把每一句都落到证据上。

## 十五、一个已经落地的工作案例

`examples/poly-2021-autumn/` 是按这份指引做出来的真实案例：

- 四份 2026-10-29 抓取的公开页面，全部保留原始 URL、逐字引文与**正文节选**（含引文的自然段与直接上下文，不是全文）；抓取时间、方式、全文 SHA-256 与裁剪范围记在 `snapshots/manifest.json`，第三方版权声明见 `THIRD_PARTY_NOTICES.md`；
- 两条真实场次：一条由两个独立家族同页共现，拿到强坐标；另一条只找到一篇雅昌原稿的澎湃号转载，按原创方归并后仍是单一来源，只到弱档；
- 两条注入的负样本：一条把日期写成 11 月 15 日，被两家独立来源直接反驳；一条凭空多出「禹贡Ⅲ」，在四份节选里没有任何说法，判"未查到"（覆盖面只到节选边界）；
- 拒绝是同一套代码算出来的，报告里能看到理由、引文与"还差什么"；
- `pnpm run demo:real` 离线重算，生成一份自包含的 HTML 报告；示例本身也进了测试。

这个案例最值得看的地方不是强记录，而是**两条被拒收的候选**：它们说明系统不是"把模型说的都包装一遍"，而是会在关键字段站不住的时候，明确地不给坐标。

在线实验不要直接写进 `examples/`。`examples/` 只放可重复的冻结底稿；实时跑的结果依赖当天的网络、模型和搜索额度，写进去会让测试变得不稳定，也会让读者分不清哪份是发布版。实验输出先落到被忽略的工作目录（例如 `.openlodestar-demo/live-<时间>/`），等结论稳定、可重复跑之后，再决定是否升级成一个新的示例。离线版可以先行发布，在线版跑通后再并列或替换。

## 十六、什么时候不该做演示

- 当产品还没有一个可核对的结论时，先别做演示；去做一次用户访谈，或者一次数据核查。
- 当素材无法公开时，用合成数据做契约测试，但不要把它包装成产品演示。
- 当演示的成本高于它能消除的疑虑时，写一页文档更划算。
- 当团队只想展示"我们做了什么"，而不是"你能核对什么"时，先停下来，回到第一原则。

演示的终点不是掌声，是观众说："我知道它凭什么算数，也知道它什么时候不算数。"
